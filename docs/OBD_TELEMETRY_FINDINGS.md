# OBD ↔ Dash Telemetry Correlation — Findings (2026-08-02)

Question we set out to answer: **does the RE dash relay live engine telemetry
(RPM / speed / coolant) to the phone over WiFi**, such that Recon Dash could show
gauges without an OBD-II dongle? Method: capture one ride with **both** the dash
link (our app, logging all `0C`/`0F` telemetry TLVs) **and** a ground-truth OBD-II
recording (Car Scanner `.brc`) running simultaneously, then correlate.

Data used:
- Dash log: ride 09:41–10:00 on 2026-08-02 (10,086 `0C` telemetry lines).
- OBD ground truth: `2026-08-02 09-41-38.brc` — healthy engine data
  (RPM 0–6488, vehicle speed 0–122 km/h, coolant 39–96 °C, 2.3k samples/PID).

> **Status: confirmation ride pending.** This verdict is from one ride. A repeat with
> Battery Saver OFF + fresh app launch is planned to remove all doubt. Note: Battery
> Saver throttles *location delivery*, not the dash's WiFi telemetry stream — the `0C`
> sampling this ride was already complete (~199 samples/channel), so the retry is
> expected to reproduce, not overturn, this result. The thing that could actually
> change it is G2 (a `0F` subscribe command), not Battery Saver — see PROTOCOL_CAPTURE.md.

## Verdict: the dash does NOT put decodable engine telemetry on the WiFi link

Evidence chain:

1. **Almost every dash `0C` sub-channel is static.** Of 26 sub-channels, 23 held a
   single constant value for the entire ride (all `00`, `AA`, or one fixed byte).
   Only three ever changed: `0x07` (drifts 232→234), `0x24` (74 distinct,
   hash/counter-like: 00,46,4C,C1,6E…), `0x26` (~232 with an end-of-ride drop to 84).

2. **None of the live channels correlate with real engine data.** Testing BE/LE and
   ÷4 decodes, and sliding ±10 s to absorb any clock skew between the two apps:
   - `0x24` vs vehicle speed: **r = +0.12**; vs RPM: **r = +0.10** — noise.
   - `0x26` vs everything: **|r| < 0.2**.
   - `0x07` scored r = −0.80 vs coolant, but this is **spurious**: it only varies
     232→234, so it is accidentally fitting coolant's slow monotonic warm-up, not
     tracking it. Its correlation to RPM/speed is ~0.1.

3. **The encrypted `0F` channel was empty this ride.** Only 2 `0F` packets arrived;
   one decrypted to `4B 31 46 00` = `"K1F\0"` (a protocol header), the other failed
   decrypt (session key not yet set at that instant). No telemetry payload.

## Why this is the expected result (the crypto + architecture reality)

- The dash protocol as we capture it is **projection-oriented**: the phone *sends*
  the rendered map / nav to the dash; the dash sends back button events and
  mostly-zeroed status flags. The bike's real RPM/gear/fuel lives on the **CAN bus**,
  which the dash does not appear to relay over WiFi.
- The `0F` channel *is* the encrypted instrument-cluster channel, and we **can**
  decrypt it — the AES-256 session key is generated by *our* client
  (`DashAuth.kt`), so our own sessions are readable. The blocker is not decryption;
  it is that the dash sent essentially no `0F` payload. Open question: is there a
  **subscribe/request command** the RE app issues that we don't? (see below).

## Consequence for the roadmap

- **Engine telemetry (RPM/gear/fuel/temp) → OBD-II/CAN is the path** (Phase 2), not
  the dash WiFi link. OBD-II can read it (proven by Car Scanner); the dash won't
  hand it to us.
- The dash link remains the right channel for **nav projection + turn glyphs**, not
  gauges.

## Two caveats before calling the dash a hard dead end for telemetry

1. **`0F` subscribe hypothesis.** If a future capture shows the **RE app** receiving a
   steady `0F` stream while our app gets ~none, that proves a phone→dash subscribe
   command we're missing. That command is in the phone→dash direction (which we can
   read), so we could replay it from our app and decrypt the resulting `0F` with our
   own key. Tracked in `PROTOCOL_CAPTURE.md`.
2. `0x24`'s changing bytes are *something* (74 distinct values), but with zero
   correlation to any PID they are unlikely to be a raw sensor — possibly packed or
   obfuscated. Low priority unless (1) turns up a payload.

## Reproducing this analysis

The decoder + correlation harness live in the (local, non-git) data dir alongside
the personal telemetry:

- `~/Developer/recon-dash-data/obd/brc_to_csv.py` — MIT-clean `.brc` → wide CSV + GPS.
- `~/Developer/recon-dash-data/obd/correlate_dash_obd.py` — time-align dash `0C`
  channels vs OBD PIDs, score Pearson r across candidate byte decodings.

```
python3 correlate_dash_obd.py <recon_dash_session.log> <carscanner.brc>
```

## Side note captured this ride — screen-off GPS

Same ride independently confirmed the screen-off GPS collapse in **both** apps:
- Nav app: screen-on median fix gap ~1.0 s (51 GPS fixes); screen-off **0 GPS**
  fixes, network-only, gaps 10–274 s.
- Car Scanner: only 8 GPS points all ride, all clustered in the two screen-on
  windows.

Two independent apps failing identically on the same device points at an OS/device
screen-off location throttle, not our code. See `SCREEN-OFF-GPS-ROOTCAUSE.md`; the
durable fix (FusedLocationProviderClient) is deferred to the next maps work cycle.
